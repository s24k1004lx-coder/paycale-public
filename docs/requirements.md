## 1. プロジェクト概要

### 1.1 背景
シフト制アルバイトでは、勤務先ごとに「締め日・給料日・時給・深夜割増・退勤時刻の丸め・最低保証時間」が違い、
市販の家計簿アプリでは「今月いくら稼げそうか」「いつ振り込まれるか」「年収の壁まであとどれくらいか」が分からない。
そこで、シフト登録から給料見込みを自動計算し、そのまま家計簿・資産推移・年収の壁管理まで一続きで見られるアプリを
自分用に作った(`PayCale`)。

### 1.2 目的
- シフトを入れるだけで、勤務先ごとのルールに沿った**給料見込み・振込日**が分かる
- 支出・収入と合わせて**手元に使えるお金・総資産の推移**が分かる
- 学生・扶養内アルバイトが気にする**年収の壁**(所得税・社会保険)を越えないよう管理できる
- 入力忘れ・シフト開始・予算超過などを**プッシュ通知**で知らせる

### 1.3 想定ユーザー
| 区分 | 内容 |
|---|---|
| 主ユーザー | シフト制のアルバイトをしている学生・フリーター(複数の勤務先を掛け持ちする人を含む) |
| 利用環境 | Android スマホ(Google Play 配信)。PWAとしてブラウザ/ホーム画面からも利用可 |
| 前提リテラシー | 設定画面で時給・締め日を入力できる程度。アカウント登録は不要にしている |

### 1.4 配信形態
単一HTMLのPWAを、TWA(Trusted Web Activity)でAndroidアプリとして包んで配信する。
**配信版は、作者が個人で使っている版とは完全に別のコード一式・別のCloudflare Worker・別のVAPID鍵**として運用する。

## 3. 機能要件

### 3.1 シフト管理
| ID | 要件 | 実装上のポイント |
|---|---|---|
| F-S1 | カレンダー(月表示・スワイプで前後月・「今日」ボタン)で日付ごとのシフトを一覧できる | `renderCalendarGridForMonth` / 3枚スライダーでスワイプ |
| F-S2 | シフトを登録・編集・削除できる(勤務先・日付・開始/終了・休憩・交通費) | `entry-modal`。休憩は0〜120分のプルダウン、交通費は計算式入力可 |
| F-S3 | 勤務先ごとに**シフトテンプレート(ピン)**を登録し、ワンタップ入力・クイックモード(テンプレ選択→日付タップで即登録)ができる | `pins` / `quick-pin-section` |
| F-S4 | 複数日選択して一括適用・一括削除ができる | `multi-select-actions` |
| F-S5 | 曜日を指定して期間内のシフトを**繰り返し一括登録**できる | `repeat-modal` |
| F-S6 | 他アプリの記録を `日付,勤務先名,開始,終了` のテキスト貼り付けで**一括インポート**できる | 設定→シフト一括インポート |
| F-S7 | 同一時間帯のシフト重複を警告する | `shift-overlap-alert` |
| F-S8 | 直前の操作を取り消せる(最大5件) | `pushUndoState` / `undoLastAction` |

### 3.2 給料計算(勤務先ごとの丸め・最低保証ルール含む)
`calculateShiftPay(shift)` の仕様(実コードの処理順そのまま):

1. **退勤時刻の丸め**: `roundEndToMin`(0=なし/5/10/15/30)。退勤の「分」をその単位で**切り上げ**、60分になれば時を繰り上げる。
2. 開始〜終了の拘束時間を求める。終了 ≤ 開始なら翌日終了(夜勤)として+24時間。
3. 実働 = 拘束時間 − 休憩。
4. **最低保証時間**: `minGuaranteedHours`(0=保証なし)。実働がそれ未満なら、実働を保証時間まで引き上げる。
5. **深夜帯**: 22:00〜翌5:00 と重なる分を深夜として計算。休憩は拘束時間に対する比率で按分して深夜側にも反映。
6. 賃金 = 日中分 × 時給 + 深夜分 × 深夜時給(未設定なら時給×1.25、小数切り捨て)。分単位で按分し、各区分で円未満切り捨て。
7. 交通費: シフト個別指定があればそれ、無ければ勤務先の「交通費/日」。給料見込みに加算。

| ID | 要件 |
|---|---|
| F-P1 | 勤務先ごとに 時給/深夜時給/交通費/丸め/最低保証/色 を設定できる |
| F-P2 | 給与計算タイプを選べる: **通常(月1回支給)** / **複数回払い(自由設定)**(支給回ごとに集計期間・支給月・支給日・土日祝調整) |
| F-P3 | 締め日・支給月・支給日から**振込日**を求め、土日祝は「前営業日/翌営業日/調整なし」で補正する(祝日は `isJapaneseHoliday`、春分・秋分・振替休日を含む) |
| F-P4 | 月ごとに勤務先別の給料見込み・支給日を表示し、実際の振込額で上書きできる(`override-pay-modal` / `actualPay`) |
| F-P5 | 金額入力欄は電卓キーボードで `+ - × ÷` の計算式を入力できる(`evaluateMath`) |

**設計理由**
- 丸めと最低保証を「勤務先の設定項目」にした理由: もともと特定の勤務先専用ルールがコードに直書きされていた(個人専用版)。
  他の利用者の勤務先でも「15分単位切り上げ」「最低N時間保証」は珍しくないため、**ルールそのものではなく『ルールを表す2つの数値』を持たせる**形に一般化した。
  新しい勤務先ルールが増えても、コード変更なしで設定だけで再現できる。
- 計算をクライアント側(端末)で完結させ、Workerには「計算済みの見込み給料」だけを渡す: サーバー側に給与ロジックを二重実装すると
  食い違いの原因になるため。

### 3.3 家計・資産管理
| ID | 要件 |
|---|---|
| F-H1 | 支出(カテゴリ: 食費/交通費/旅費/交際費/日用品/趣味/固定費/小銭貯金/その他、メモ、金額)・その他収入(立て替え回収/お小遣い/フリマ/副業/キャッシュバック/その他)を記録できる |
| F-H2 | 支出テンプレート(ワンタップ入力)、過去の入力からのワンタップ入力 |
| F-H3 | 固定費の自動登録(毎月・支払日つき・**円以外の通貨**対応。為替は `frankfurter.app` から取得し参考表示。総資産計算には反映しない) |
| F-H4 | **総資産**: 基準日の資産額(ベース)+ 以降の給料見込み+その他収入−支出 で日付ごとに算出。過去日は逆算 |
| F-H5 | 月間支出予算・貯金目標・**カテゴリ別予算上限**を設定でき、進捗バー・先月/前年同月との比較を表示する |
| F-H6 | 統計: 総資産推移(過去21日・今後9日)、勤務先別給料見込み推移、月別収支推移、日別支出推移、カテゴリ別ドーナツ(Chart.js) |
| F-H7 | **年収の壁トラッカー**: 106/130/150/160/201万円/カスタムを目標に累計・残額を表示 |
| F-H8 | **税金・社会保険の簡易診断**: 勤労学生の有無で所得税の非課税ライン(150万/160万)を切替、106万・130万の壁を判定し概算額を提示(目安である旨の注記つき) |
| F-H9 | 「今日のランダム小銭貯金」ガチャ(500円未満) |
| F-H10 | データ出力: CSV、年間給料一覧CSV(確定申告用)、JSONバックアップ/復元、.ics 書き出し |
| F-H11 | 任意のクラウドバックアップ: GitHub Gist(利用者自身のトークン。端末内にのみ保存、保存のたび自動バックアップも可) |

**設計理由**
- 全データを端末の `localStorage`(キー `SHIFT_PRO_DB`)に持つ: アカウント登録・サーバーDB・認証が不要になり、個人情報をサーバーで預からずに済む。
  (代わりに、端末紛失・ブラウザデータ消去に備えて JSON/Gist バックアップを用意している)
- 壊れたデータを検知したら上書きせず `SHIFT_PRO_DB_BROKEN_BACKUP_<時刻>` に退避して初期状態で起動する(データ喪失の二次被害を防ぐ)。
- 税制の判定ラインは改正で変わるため、診断結果には必ず「目安」の注記を出し、判定基準日をコード内コメントに残している(`runTaxDiagnosis`)。

### 3.4 プッシュ通知
| ID | 通知 | 条件・仕様(`worker/index.js` の `processUser`) |
|---|---|---|
| F-N1 | 入力忘れリマインダー | 設定時刻から15分以内に、その日まだ送っていなければ1回。 |
| F-N2 | シフト開始前通知 | 開始の「N分前」(0〜1440分)から15分以内に1回。勤務先・時間・見込み給料・応援メッセージ入り。送信対象は今日〜明後日のシフト |
| F-N3 | 予算超過通知 | カテゴリ別上限に使用額が達したら、月ごと・カテゴリごとに1回 |
| F-N4 | 固定費の支払日通知 | 支払日当日の9:00(JST)以降の最初のcronで1回。31日指定は月末扱い |
| F-N5 | テスト通知 | 設定画面から送信。同一uidは60秒に1回まで |
| F-N6 | サーバー状態確認 | 設定画面から `/health` を確認 |

**設計理由**
- cron(5分おき)判定を「ぴったり一致」から「**幅(15分)+送信済み記録**」に変えた: Cloudflare の cron は数分遅れる/まれに欠けるため、
  ぴったり一致だと通知が欠落する。送信済みキー(`st:<uid>`)で重複は防ぐ。(通知の信頼性 §5.4)
- 固定費通知を0:00台から9:00以降に変えた: 深夜に鳴らさないため。
- 通知の内容(シフト・予算・固定費)は**端末がWorkerに送った最新の集計**を使う。端末が起動していなくても通知できるようにするため。
- 同じ `tag` の通知は上書きされる(再送時に通知が積み上がらない)。

### 3.5 カレンダー同期
| ID | 要件 |
|---|---|
| F-C1 | 「カレンダー同期を有効にする」で全シフトをWorkerに送り、`/calendar.ics?token=…` を購読URLとして提示する |
| F-C2 | iPhone: `webcal://` リンクで標準カレンダーに登録。Android: URLをGoogleカレンダー(Web)の「URLで追加」に貼る(購読の更新は数時間おき) |
| F-C3 | 日をまたぐ夜勤は翌日終了のイベントにする。タイムゾーンは `Asia/Tokyo` 固定 |
| F-C4 | 同期ONの間は、シフト変更のたびに(4秒デバウンスで)再送する |

**設計理由**: 購読形式(.ics)にしたのは、Googleカレンダー等の外部APIの認可(OAuth)を使わずに、**利用者のアカウント連携なし**で実現できるから。
購読URLには `uid` を載せず `token` だけにした(URLを人に見せても通知設定を書き換えられないようにするため。§5.1)。

### 3.6 オンボーディング
初回起動(`onboardingDone=false` かつ勤務先が0件)にモーダルを表示:
1. ようこそ(「はじめる」/「あとで設定する」)
2. 勤務先名・時給・交通費(丸め・最低保証は後から勤務先編集で設定)
3. 現在の総資産(任意。総資産推移の起点)

**設計理由**: 配信版は初期データを空にしたため、そのままでは何も入力できない画面になる。最小の入力(勤務先1件+資産)だけで使い始められるようにし、
細かいルールは「後から設定」に逃がして離脱を減らす。

### 4.2 主要コンポーネント
| コンポーネント | 役割 | 技術選定の理由 |
|---|---|---|
| `public/index.html` | UI・全ロジック・データ保持 | 単一ファイルでビルド不要。個人開発で変更→即確認でき、静的ホスティングだけで配信できる |
| `public/sw.js` | キャッシュ・Push受信 | PWA要件。Push は Service Worker でしか受けられない |
| `public/manifest.json` | PWAメタ情報(maskableアイコン含む) | TWA化(Bubblewrap)がここから生成する |
| `worker/index.js` | 通知の送信・判定、.ics配信 | サーバー常駐不要・無料枠で足りる・cron内蔵。VAPID署名を端末外で行える |
| Cloudflare KV | 通知用の最小データ | キー単位でuid分離でき、実装が単純。(規模が出たらD1へ。§9) |
| Bubblewrap/TWA | Androidアプリ化 | Webを書き換えずにGoogle Play配信できる。更新はWeb側のデプロイだけで反映(アプリ再審査不要) |

### 4.3 API(フロント ⇔ Worker)
すべてPOSTで本文に `uid` を含める。`uid` は端末で生成した推測困難なランダムID(32桁16進)。

| エンドポイント | 本文 | 保存先 |
|---|---|---|
| `POST /subscribe` | `{uid, subscription}` | `sub:<uid>`(送信先ホストは FCM/Mozilla/Apple/Windows のみ許可) |
| `POST /reminder` | `{uid, enabled, time}` | `cfg:<uid>` |
| `POST /shift-alert-settings` | `{uid, enabled, minutesBefore}` | `cfg:<uid>` |
| `POST /shifts` | `{uid, shifts[]}`(今日〜2日後) | `shifts:<uid>` |
| `POST /budget-status` | `{uid, month, items[]}` | `budget:<uid>` |
| `POST /fixed-expenses` | `{uid, items[]}` | `fixed:<uid>` |
| `POST /calendar-shifts` | `{uid, token, shifts[]}` | `cal:<uid>`, `calidx:<token>` |
| `POST /test` | `{uid}` | (`rl:<uid>` で60秒制限) |
| `POST /delete` | `{uid}` | 当該uidの全キーを削除 |
| `GET /calendar.ics?token=` | — | tokenで逆引きして配信 |
| `GET /health` | — | `{ok,time,vapid(公開鍵先頭12字)}` |

## 5. 非機能要件

### 5.1 マルチユーザー時のデータ分離・プライバシー
| ID | 要件 | 実現方法 |
|---|---|---|
| N-P1 | 利用者のデータが他の利用者と混ざらない | すべてのKVキーに uid を含める。uid 不正は400。固定の共用ID(例: "anonymous")にフォールバックしない(端末に保存できない場合は連携を使わせない) |
| N-P2 | サーバーに送る個人情報を最小化 | 送るのは §4.3 の項目のみ。**支出・収入の明細、資産額、メモ、GitHubトークンは送らない**。カレンダー同期は利用者がONにした場合のみ全シフト(勤務先名・時間・見込み給料)を送る |
| N-P3 | カレンダーURLの秘匿 | token は端末生成の推測困難な値。URLには uid を載せない。Worker は token が一致しない/未登録は同じ403(存在を探らせない)。一度決まった token は変更不可、他人の token の紐付けも拒否 |
| N-P4 | 不正な購読先への送信禁止(SSRF対策) | Push の送信先 endpoint のホストを許可リストで検証 |
| N-P5 | 乱用対策 | 本文サイズ上限(1MB)、件数上限(シフト5000/固定費100/予算50)、`/test` は60秒1回 |
| N-P6 | 利用者がデータ削除を求められる | `POST /delete`(現状UIなし。§9) |
| N-P7 | 秘密鍵をソースに置かない | `VAPID_PRIVATE` は `wrangler secret`。公開鍵のみ `wrangler.toml` とフロントに記載 |
| N-P8 | 個人用環境との分離 | 別Worker名・別KV・別VAPID鍵。個人用の値(URL・鍵・token・勤務先名)はコードから除去済み |

**残るリスク(受容)**: uid を知る者は、その uid の通知設定を書き換えられる(uid は端末外に出ないため通常は問題にならない)。
将来はデバイス秘密鍵による署名(HMAC)に強化できる。

### 5.2 オフライン対応(PWA)
- アプリ本体・アイコン・manifest・Chart.js を Service Worker がキャッシュし、**機内モードでも起動・入力・集計・グラフ表示が可能**。
- 画面遷移は「ネット優先、失敗時キャッシュ」(更新を早く反映)、静的ファイルは「キャッシュ優先+裏で更新」。
- Worker・Gist・為替APIなど**外部APIはキャッシュしない**(古い応答を返さない)。
- データはlocalStorageなのでオフラインでも読み書きできる。通知関連の同期だけが、復帰後のデバウンス再送になる。
- Chart.js はバージョンを固定した(`@4.4.7`)。未固定だと、ある日メジャー更新が入ってグラフが壊れ、オフラインキャッシュも更新で揺れるため。

### 5.3 Android配信形式(TWA)
- 配信方式は **TWA(Bubblewrap)**。Chrome の機能(Web Push・Service Worker)をそのまま使え、Webの更新がアプリに即反映される。
- 前提: HTTPS・manifest(192/512 の any と maskable アイコン)・Service Worker・**Digital Asset Links**(`/.well-known/assetlinks.json`)。
  assetlinks が無い/指紋が違うとURLバー付き(Custom Tabs表示)になる。
- 通知は `enableNotifications: true`(通知デリゲーション)で、TWAからでもWeb Pushを受け取れる。
- 署名: Google Play App Signing を使う。assetlinks には **Play側の署名鍵のSHA-256**(と、実機で直接入れる場合はアップロード鍵のSHA-256)を登録する。
- 配信先のホスト名は**アプリに焼き込まれ後から変えられない**ため、最初から長く使えるドメインにする。
- 詳細手順: [ANDROID_SETUP.md](ANDROID_SETUP.md)

### 5.4 通知の信頼性
| 課題 | 対策 |
|---|---|
| cronの遅延・欠落 | 判定に15分の幅 + 送信済み記録(`st:<uid>`)で「欠落しない・重複しない」 |
| 購読の失効(アンインストール等) | 404/410 を受けたら購読をKVから削除し、以降の送信・読み取りを止める |
| 古い通知が遅れて届く | Push の TTL を1時間にして、期限切れの「まもなくシフト開始」を出さない |
| 同じ通知の重複表示 | `tag` を付けて上書き |
| 1人の失敗が全体に波及 | 利用者ごとに try/catch。並列10件ずつ処理 |
| 設定とサーバー状態のズレ | 通知を有効にした直後に、リマインダー・シフト設定・直近シフト・予算・固定費を一括で再送する |
| Workerの稼働確認 | 設定画面の「通知サーバーの状態を確認」(`/health`) |
| 鍵の不一致(送信できない) | `/health` の `vapid` とフロントの公開鍵を見比べる。`scripts/check-vapid.mjs` で秘密鍵と公開鍵の対応を検証 |

**既知の制約**: KVのread/writeと、cronのサブリクエスト数には上限がある。利用者が数十人を超える規模(特に無料枠)では
cronの処理量が上限に近づく。そのときはD1(SQL)に移し、`WHERE 通知予定時刻 <= now` で対象だけ引く構成に変える(§9)。

### 5.5 その他
- パフォーマンス: ビルド不要の単一HTML(約330KB)。グラフはChart.js。
- 保守性: 計算ロジックは `calculateShiftPay` 1か所。Worker側は見込み給料を再計算しない。
- ブラウザ要件: Android Chrome(TWA)。iOSは §7。

## 7. 制約・スコープ外(今回やらないこと)

### 7.1 スコープ外
- **iOS版**(App Store配信)。Web Push は iOS ではホーム画面追加(PWA)でのみ動き、ストア配信にはネイティブ化が必要で、今回の対象外。ただしPWAとしては iOS でも動く(カレンダー購読は iPhone 向けの `webcal://` リンクあり)
- アカウント登録・ログイン・端末間の自動同期(データは端末内+手動/Gistバックアップ)
- 課金・広告
- 多言語化(日本語のみ)、日本以外の税制・祝日
- 通知の送信先を端末ごとに複数持つこと(1 uid = 1 購読)

### 7.2 制約
- 税制判定は目安(改正で変わる)。診断画面に注記済み
- Android で TWA の「カレンダー同期」は購読URLの手動登録(Googleカレンダーは購読の更新間隔が長い)
- データが端末内のため、Chromeのサイトデータ消去・機種変更で失われる(バックアップ機能で補う)
- ブラウザ標準の `localStorage` 容量上限(約5MB)

### 7.3 AI機能廃止の経緯 ※要確認
- 個人用版には、支出・稼働・予算のサマリーを Workers AI(Llama系モデル)に送ってアドバイスを返す機能(`POST /advice`)があった。
- 配信版では **Worker側のエンドポイントを削除**し、フロントも `initAiAdvice()` を即returnして、カードは非表示にしている(`ai-advice-card` は `display:none`)。
- 推定される理由(作者の意図と合うか確認すること): (1) 不特定多数が使うとAI推論の無料枠・コストを共有して使い切る/乱用される、
  (2) 家計の集計データを外部AIに送る機能は、プライバシーポリシーと Play の「データセーフティ」申告が重くなる、
  (3) 3Bクラスの小型モデルは助言の質が安定しない。
- 現状はフロントに**未使用のコード(`fetchAiAdvice` / `buildSpendingSummary` など)が残っている**。将来再導入しないなら削除してよい。

## 8. 設計判断の記録(要約)
| # | 判断 | 理由 | 却下した案 |
|---|---|---|---|
| D1 | 単一HTML + localStorage | ビルド・DB・認証が不要。個人情報をサーバーで預からない | React等のSPA+DB(初期コストが過大) |
| D2 | PWA→TWA | Webの更新が即反映。Web Push をそのまま利用 | Capacitor/Flutter(ネイティブ化の工数。Push/ファイルが不安定な場合のみ検討) |
| D3 | uid(端末生成)で分離、ログインなし | 登録不要で離脱を減らし、パスワードを預からない | メール/OAuthログイン |
| D4 | Worker+KV | 無料枠・cron内蔵・運用不要 | 常駐サーバー、Firebase |
| D5 | 給与計算は端末側のみ | ロジックの二重実装による食い違いを避ける | Worker側でも計算 |
| D6 | ルールを「設定値」に一般化 | 勤務先ごとの差を、コード変更なしで吸収 | 勤務先ごとの分岐コード |
| D7 | 秘密鍵は secret | ソース公開・流出時の被害を避ける | ソースに直書き(個人用版はそうだった) |
| D8 | cron判定に幅+送信済み記録 | 取りこぼしと重複の両方を防ぐ | ぴったり一致 |
| D9 | カレンダー購読URLは token のみ | URL共有でuidが漏れない | uid+token(旧設計) |

## 9. 今後の拡張候補
優先度の目安: 高=公開前に検討 / 中=公開後 / 低=余裕があれば

| 優先 | 候補 | メモ |
|---|---|---|
| 高 | プライバシーポリシー・設定画面の「サーバー上のデータを削除」ボタン(`/delete` 連携) | Play公開に必須(ポリシーURL)。Worker側は実装済み |
| 高 | 未使用のAIコードの削除、`kyoeiAbolishDate` など旧名称の変数名整理 | 可読性・面接での説明のしやすさ |
| 中 | 通知購読の自動更新(`pushsubscriptionchange`) | SWからuid/Worker URLを参照する仕組み(IndexedDB等)が必要 |
| 中 | 勤務先ルールのプリセット(丸め・最低保証のテンプレ) | オンボーディングの入力をさらに減らす |
| 中 | 端末間のデータ同期/引き継ぎコード(QRやJSON) | 機種変更時の損失を減らす |
| 中 | 自動テスト(`calculateShiftPay` の単体テスト、Workerテストは整備済み) | 給与ロジックの退行防止 |
| 低 | 認証強化(デバイス秘密鍵のHMAC署名) | uid の秘匿性への依存を減らす |
| 低 | 規模拡大時: KV → D1、cronのキュー分割 | §5.4 の既知の制約 |
| 低 | Capacitor移行 | ネイティブPush/ファイルアクセスが必要になった場合 |
| 低 | iOS対応 | §7.1 |
| 低 | AIアドバイスの再導入(オプトイン・端末内ルールベースを先に検討) | §7.3 |
